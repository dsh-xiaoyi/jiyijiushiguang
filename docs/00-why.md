# 为什么做这个东西

> 第一次读到这里，不必一次记住；先照着跑一遍，遇到问题再回来查对应那一节。
## 起因：一个会话越聊越长，人越来越陌生

我们一开始只有一台机器、一个智能体。聊到深夜，它开始把前一天刚定好的规则忘掉，
再后来是"我明明说过"变成"你是不是记错了"。

它不是变坏了。**它每次只看得见最近一小段上下文**——而那一段里，没有我们定过的东西。

于是我们做了第一版"记忆库"：把对话、决定、教训都存进 SQL，再想办法塞回上下文。
第一版是失败的，而且失败了三次（详见 `02-memory-design.md` 的"三层缺陷"）：

```
① 注入永远是空的      —— 配置指向一个不存在的脚本，"加载成功"但什么都没注入
② 只注入最新 8 条     —— 库里有 1500+ 条，8 条窗口只看得到最近几小时
③ 有检索但没有 IDF    —— 常见词淹没稀有词，检索在跑，却永远答不到点上
```

三次都**不报错**。这是最贵的一类缺陷：系统看起来一切正常，只是"它不记得你了"。

## 后来：一台机器不够，就有了集群

加机器解决的是另一类问题：算力、试错空间、备份冗余。
但一旦有多台，就多出三个新问题：

1. **每台各记各的** → 共享一个记忆库，但要有"谁在什么时候说了什么"的可追溯性
2. **传话不可靠** → 实时通道只发"现在就要"的，重要的事必须走可重试的队列
3. **坏了没人知道** → 每台机器都要能被另一台探到；探不到 = 出事，而不是"它可能在忙"

## 为什么开源

因为这些问题不是我们独有的。任何把 DSH 用到"长期、多机、要它记住约定"的人，都会撞上：

- 会话变长之后的失忆（而且要等它变得很长才暴露，最坑）
- 改了插件没重启，改动静默失效
- 备份看起来有，恢复起来没演练过
- 多机传话靠聊天，对方空闲就丢了

我们把这些写下来，不是为了展示"我们的方案多好"，而是为了把**踩过的坑**变成别人可以绕开的路标。

## 这个仓库的定位

```
它不是模型的替代品，而是"让模型记得住、查得到、坏了能修"的运维框架。
它不炫技：没有内核驱动、没有自研反病毒、没有"杀不掉的自保护"。
它承认自己会坏：所以每个判据都要能自己证明自己没坏（一义、有分母、不抖动）。
```

## 写给未来的维护者（包括未来的我们）

```
如果你读到这段时，发现某条规则"看起来多余"，请先查 04-postmortems.md。
它大概率是某次事故换来的。
```
