# dsh-memory-bridge 的加载 / 热重载行为（实测记录，2026-10-06）

## 一、实用规则（照这个做就行）

> **改了插件目录里的任何文件（`index.mjs` / `verify.mjs` / `cordis.patch.yml`）之后，请重启 DSH。**
> **不要指望 HMR 自动应用 —— 实测至少有一种情况它不会。**

## 二、唯一可靠的判据

```
<插件目录>\bridge.log   出现，且内容含  "auto-capture armed"
```

- `bridge.log` 是 **v0.2.0 起新增**的；v0.1.0 没有这个文件。
- ★ **不要**用"profile 列表里有这个包"当判据 —— 那只说明**装上了**，不说明**加载了**。
- ★ **也不要只看注入段落** —— 注入部分是同步返回的字符串，很容易"看起来在跑"。
- v0.1.0 的判据只能用：新会话系统提示里是否出现「## 共享长期记忆」段落。

## 三、实测记录（三台中的中枢节点，2026-10-06 凌晨）

| 时刻 | 动作 | 结果 |
|---|---|---|
| 00:07 | 装入 desktop profile（**新增 bundle，profile 真的变化了**） | ★ **免重启即生效**：运行时上下文出现注入段落，而 DSH 主进程仍是 23:09 启动的 |

## 四、关于机制（两个候选解释，尚未定论，别当结论引用）

- **A. 只有「profile 层真的变了」才会触发重载**；改插件目录里的文件不算变化。
  —— 与上表三行全部一致（第 1 行是唯一"真变化"的一次）。
- **B. 新增 `ctx.on('session/event')` 这类「事件订阅」不会被热应用**（只改注入逻辑时能热更）。
  —— 未能单独验证。

请以 **A** 为默认假设：**改完插件就重启**；要免重启更新，得让 profile 层发生真实变化（本机未验证可靠，不建议依赖）。

## 五、给以后写插件的人的提醒

1. 插件**一定要有自己的落盘日志**（像 `bridge.log`）——"装了但没生效"是这类集成最难发现的一类失败，
   而且它**不会报错**，只会安静地什么都不做。
2. 日志里写一句明确的"已武装"标记（如 `auto-capture armed`），比事后猜有用得多。
3. 自检脚本（`verify.mjs`）用**临时日志**，不要污染真实日志 —— 否则就分不清"自检过的"和"宿主加载的"。
   （本插件的 `verify.mjs` 已经这么做，值得沿用。）
4. 中文字符串一律走 **UTF-8 文件传参**，不要经过命令行引号（我们踩过这个坑）。
